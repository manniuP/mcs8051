# 26 上游跟进方案（Zig → 1.0）

> 目标：让**自研 MCS 后端**能尽快跟上 Zig 上游（含 1.0）。原则：**只维护我们写的 delta**，
> 上游文件尽量少动；把 delta 做成「上游更新时只需 rebase + 重放少量接入」的形态。
> 相关：后端框架见 `mcs251/docs/25-MCS后端框架.md`；发布同步见 `docs/发布同步策略.md`。

## 0. 现状（好消息：已经是上游直系后代）

- fork 仓 = `<workspace>/zig`（分支 `mcs251-backend`），远程：
  - `mirror` → `https://codeberg.org/ziglang/zig.git`（**上游**）
  - `backend` → `git@github.com:manniuP/zig-mcs51-backend.git`（我们发布用）
- 我们的提交**线性叠在上游之上**（上游 base `7056ba9a5c` 是 `40b3dad246 feat(mcs): 加入后端` 的父提交）。
  ⇒ 跟上游本质就是 **rebase**，不需要手工搬运。
- 但**开发副本有两份**：`mcs251/compiler/`（内联，日常开发）与 `<workspace>/zig`（fork 工作树）。
  两者当前几乎一致，差异仅在 `mcs251` 里未提交的改动 ⇒ 有**漂移风险**（见 §3）。

## 1. 我们的 delta（= rebase 冲突面，仅此而已）

**A. 纯新增（几乎永不冲突）**

```
compiler/src/codegen/mcs/{CodeGen,Mir,encode,forms,abi,device}.zig
compiler/src/link/Asx.zig
```

**B. 上游接入 patch（~180 行 / 11 文件；rebase 时唯一可能冲突处）**

| 文件 | 改动意图 | 冲突概率 |
| --- | --- | --- |
| `src/codegen.zig` | 后端 dispatch（`stage2_mcs` 分支/AnyMir/emit/generateLazy）+ 指针宽处理（`lowerUavRef/lowerNavRef` 加 `u24`）+ `undefPtrBits`（64 位溢出修复） | 中 |
| `src/target.zig` | arch `mcs51/mcs251`：`zigBackend→stage2_mcs`、地址空间默认/转换 | 中 |
| `src/Zcu.zig` | `callconvSupported(.stage2_mcs)` 认 `.mcs51_sdcc/…interrupt` | 低 |
| `src/Sema.zig` | 变参调用约定白名单加 `.mcs51_sdcc/.mcs251_sdcc` | 低 |
| `src/Type.zig` | `ptrAbiAlignment` 支持非 2 幂字节宽（3 字节指针 → 对齐 1） | 低 |
| `src/dev.zig` | 加 `mcs` 精简 env + `mcs_backend`/`asx_linker` 两个 Feature | 中 |
| `src/link.zig` | 加 `.asx` 链接器 tag（hex → asx） | 中 |
| `src/codegen/llvm.zig` | 新 arch / 新调用约定在 LLVM 分支的占位（`unreachable`） | 低 |
| `src/codegen/spirv/Module.zig` | 新 AddressSpace 在 SPIR-V switch 里的占位 | 低 |
| `lib/std/Target.zig`、`lib/std/builtin.zig` | 新 arch（mcs51/mcs251）与调用约定/地址空间钩子 | 中 |

> 保持 **B 与 A 分成不同 commit**（当前 fork 里 `40b3dad246` 是 A+接入混在一起，后续新工作可拆）。
> 这样 rebase 时 A 不动，冲突只在 B。

## 2. 跟进流程（上游更新 / 1.0）

```bash
cd mcs251/compiler                       # fork 工作树（已改为 submodule）
git fetch mirror                         # 取上游最新（或 1.0 tag；需先加 mirror 远程，见 §3）
git rebase mirror/master                 # 或：git rebase --onto <1.0-tag> 7056ba9a5c mcs251-backend
# 冲突集中在 §1-B 的 9 个文件；按「意图」把对应分支/枚举项重新插桩
#   git grep -n 'stage2_mcs' 确认所有 dispatch 点仍然存在
#   git grep -n 'mcs51\|mcs251' 补新出现的 exhaustive switch
zig build                                # 或 -Dmcs-only（见 §4）
git push backend mcs251-backend          # push 先问用户
```

配套检查：
- `python tools/gen_mcs_forms.py` 重生成 `forms.zig`（若指令集/`std.Target` 有变，需重编后再测）。
- `python tools/compiler_sync_check.ps1`（本仓）比对 `compiler/` 与 fork 工作树，防漂移。

## 3. 单一真源（已完成：`mcs251/compiler` = submodule）

`mcs251/compiler` 已从「内联源码」改为 **submodule**：
`url = git@github.com:manniuP/zig-mcs51-backend.git`，`branch = mcs251-backend`。

- **开发 / 提交 / rebase 都在 `mcs251/compiler`**（它就是 fork 的工作树）；原先两份源码的漂移问题消除。
- 跟上游前，先在 `compiler/` 里挂一次上游远程（codeberg ziglang，仅需一次；勿把本地绝对路径写进仓库）：
  ```bash
  cd mcs251/compiler
  git remote add mirror https://codeberg.org/ziglang/zig.git   # 与 fork 仓里同名
  git fetch mirror
  ```
- 原 `<workspace>/zig` clone 现在**冗余**（可选择保留作上游镜像，或删除；删大件前先确认）。
- `tools/compiler_sync_check.ps1` 改为自检用（对比 `compiler/` 与可选镜像）；发布按 `发布同步策略.md`。

## 4. 加快迭代的现成手段

- `-Dmcs-only`：只编入 MCS 后端，自举/验证更快（见 `AGENTS.md`）。
- 构建层优化与回归：`docs/25-MCS后端框架.md` §5、`docs/24-优化器管线总览.md`。
- 后端框架与「改哪儿」：`docs/25`。

## 5. 上游 1.0 到来时的清单

1. `git fetch mirror` → rebase 到 1.0（§2）。
2. `git grep -n 'stage2_mcs\|mcs51\|mcs251'`：确认 dispatch/枚举/switch 全覆盖（上游会增删后端/地址空间/调用约定）。
3. 重生成 `forms.zig`，自举重建（先经确认）。
4. 跑 `tools/ci.ps1`（构建 + self-test + 8 位仿真 + 预算回归）。
5. `cd mcs251/compiler && git push origin mcs251-backend`（push 先问）→ 按 `发布同步策略.md`
   同步 `mcs8051` 的 `compiler` 子模块指针。
